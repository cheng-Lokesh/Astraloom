# Astraloom 白皮书实现基准 v36

版本：v36 现实优先路径沙盘版  
状态：当前产品方向与工程实现的约束基准  
来源：基于旧版 MiroFish / Astraloom 白皮书、当前产品 UX North Star、前端设计系统与主流程审计更新

## 1. 产品一句话定义

中文：

> Astraloom 会先理解你的现实处境，再用命理气候作为时间视角，推演几种未来路径可能如何展开。

English:

> Astraloom grounds your real-world situation first, then uses destiny climate as a timing lens to simulate possible future paths.

Astraloom 不是普通命理软件，不是聊天机器人，不是后台控制台，也不是 RPG 剧情游戏。它是一个现实优先、命理调权、路径推演的个人未来路径模拟工具。

## 2. 产品北极星

Astraloom 的核心体验是：

1. 用户提交一个真实案例。
2. 用户提供现实问题、现实材料和时间窗口。
3. 系统通过 DeepSeek Reality Intake 抽取现实结构。
4. 系统在可用时接入外部现实来源，形成有来源支撑的现实社会模型。
5. 命理只作为时间气候和用户反应倾向的调权层。
6. 系统推演几条可能路径如何展开。
7. 结果展示关键发现、现实依据、命理调权、不确定性和下一步观察。

产品可信度来自现实材料、来源依据、路径事件和不确定性披露，而不是来自神秘感或确定性预言。

## 3. 产品不是什么

Astraloom 明确不是：

- 算命报告
- 命理神谕
- 聊天机器人
- 后台控制台
- RPG 剧情游戏
- 高确定性预测器
- 读心工具
- 专业法律、医疗、金融或心理建议替代品

禁止把结果表达成“必然”“注定”“一定会”“克你”或“系统知道某人的真实想法”。

## 4. 产品是什么

Astraloom 是以下能力的组合：

- 现实信息摄取
- AI 现实节点抽取
- 外部现实来源 grounding
- 现实社会模型构建
- 命理时间气候与反应倾向调权
- 多路径演化模拟
- 依据回放
- 不确定性提示
- 下一步观察建议

旧版白皮书中以 Agent / NPC / 关系图谱为第一主语的叙事，需要降级为内部实现或高级结构语言。普通用户看到的主体验应围绕“现实案例、现实节点、压力、路径、发现、依据、观察”展开。

## 5. 用户心理模型

用户进入产品时应该感觉：

- 我正在提交一个真实案例。
- 系统在读取现实信息。
- AI 在帮我抽取现实结构。
- 外部来源在帮助校验部分现实背景。
- 命理只是解释我的反应倾向和时间气候。
- 系统把几条路径展开给我看。
- 我能看到每个结论的依据。
- 我知道哪里还不确定。

用户不应该感觉：

- 我在填命理表单。
- 我在和聊天机器人闲聊。
- 我在操作后台控制台。
- 我在玩剧情游戏。
- 系统在替我做确定性人生决定。

## 6. 信息层级原则

主视图只展示：

- 当前推演能力状态
- 现实材料 / 现实节点
- 关键路径
- Top findings
- 下一步观察

折叠区展示：

- Debug
- raw event
- technical IDs
- graph details
- evidenceEventIds
- traceId
- modelVersion
- writerVersion

工程字段必须保留，但不能压主体验。用户需要先理解“为什么可信、哪里不确定、下一步观察什么”，再进入技术检查。

## 7. 每个页面只回答一个核心问题

### Dashboard

核心问题：

> 这是什么？现在能不能真实推演？我从哪里开始？

页面必须突出：

- 产品定义
- 当前能力状态
- 是否 source-backed
- 主 CTA：开始真实案例
- 示例入口

不得把首页做成流程入口列表或后台导航页。

### Start

核心问题：

> 我要提供什么，才能让推演更可信？

页面优先级：

1. 当前现实问题
2. 现实材料
3. 出生信息
4. 当前能力状态
5. 生成沙盘

出生信息属于命理调权层，不是主输入。现实材料越具体，沙盘越能基于现实推演，而不是本地假设。

### Running

核心问题：

> 系统正在如何把现实信息变成沙盘？

页面必须展示：

- 当前模式
- 是否有现实来源支撑
- DeepSeek 是否参与
- 外部现实来源是否参与
- 阶段进度：读取现实问题、AI 抽取现实节点、检索外部现实来源、建立现实社会模型、应用命理调权、推演可能路径、整理关键发现
- 现实节点、现实压力、外部来源、缺失信息
- 命理调权卡
- 四条路径对比

未启用 API 的阶段不能假装完成。fallback 必须明确。

### Result

核心问题：

> 这次推演最重要的发现是什么？为什么可信？哪里不确定？

第一屏必须回答：

- 这次推演是否 source-backed
- Top 3 findings
- 每条发现来自现实依据、AI 抽取、外部来源、命理调权还是路径事件
- 置信度与不确定性
- 下一步应该观察什么

Debug 默认折叠到底部。

## 8. 命理展示原则

命理只能作为：

- 时间气候
- 用户反应倾向
- 压力敏感度
- 机会响应方式
- 边界风格
- 路径调权

命理不能：

- 创造现实人物
- 创造现实事实
- 断言某个人一定存在
- 断言未来必然发生
- 抢占现实依据
- 提高结果置信度
- 替代现实来源或用户材料

推荐表达：

- “命理气候会影响你在这个时间窗口中对压力的敏感度。”
- “这个调权只改变路径反应倾向，不生成现实事实。”
- “在当前信息下，这条路径更值得观察。”

禁止表达：

- “命盘说明这个人一定会出现。”
- “这件事注定发生。”
- “对方真实想法是……”

## 9. Runtime Capability 原则

全站必须让用户知道当前模式：

- local_assumption
- manual_reality
- ai_reality_intake
- external_reality
- full_grounded_reality

模式规则：

- local_assumption：不能包装成真实推演，只能称为本地假设演示或结构预览。
- manual_reality：可以使用用户提供的现实材料，但不能声称联网验证。
- ai_reality_intake：可以说明 AI 已抽取现实结构，但不能声称外部来源参与。
- external_reality：可以强调外部现实来源已参与，可用于第一轮真实推演试用。
- full_grounded_reality：可以说明 DeepSeek、现实材料和外部来源均已参与，但仍要保留不确定性。

Runtime 状态必须始终可见，但不应以大面积 warning 压垮首页。

## 10. 视觉与交互原则

视觉方向：

- warm ivory background
- soft green accent
- deep ink contrast
- calm source-backed evidence cards
- restrained motion
- premium consulting tool
- not mystical
- not gamified
- not dashboard-like

交互原则：

- 主流程 CTA 明确。
- 高级入口弱化。
- Debug 默认折叠。
- 技术 ID 不进入主视图。
- 卡片层级区分主体验、辅助信息、命理调权和 Debug。
- 移动端表单单列，按钮易点击，标签可换行，长文本不撑破页面。

禁止：

- 星空、塔罗、紫色神秘、符文、水晶风
- RPG 化选择循环
- 后台化 KPI 密度
- 过度动画
- 大型 UI 框架
- 让命理创造现实

## 11. 现实 grounding 与证据结构

Astraloom 的可信度来自证据链，而不是来自语言气势。

每个重要发现应尽量回到以下来源：

- 用户手动现实材料
- DeepSeek Reality Intake 抽取结果
- 外部现实来源
- 现实压力 / 现实节点
- 路径事件
- 命理调权依据
- 缺失信息与不确定性

如果外部来源不可用，结果必须清楚标注不是完整现实推演。如果 DeepSeek fallback，必须清楚告知用户。

## 12. 四条路径原则

默认路径对比：

- 当前惯性
- 谨慎观察
- 主动推进
- 边界调整

每条路径展示：

- 用户动作
- 现实反应
- 压力变化
- 信息变化
- 机会变化
- 命理调权
- 置信度
- 需要继续观察的信号

路径语言必须保持非确定性：

- 可能
- 更容易
- 值得观察
- 需要验证
- 在当前信息下

## 13. 安全、边界与合规

Astraloom 必须明确：

- 结果是模拟与观察辅助，不是专业建议。
- 不替用户做最终决定。
- 不断言他人真实想法。
- 不根据命理制造事实。
- 不把低置信结果包装成确定判断。
- 不通过付费提高置信度或改变结论方向。

高风险输入必须触发降级、提醒或拒绝，而不是生成强建议。

## 14. 商业化原则

当前工程实现不接支付，不应引入支付逻辑。

未来如果设计商业化，用户付费购买的也只能是：

- 更完整的证据回放
- 更长的路径比较
- 更多现实材料整理
- 更系统的观察清单
- 更好的校准与复盘工具

用户不能付费购买：

- 更确定的命运
- 更高 confidence
- 被隐藏的恐惧结论
- 对他人真实想法的断言
- 绕过安全降级

## 15. 当前工程验收基准

当前主流程验收：

- Dashboard 像产品首页，不像后台。
- Start 像真实案例提交页，不像命理表单。
- Running 像沙盘展开过程，不像系统日志。
- Result 像现实推演报告，不像 claim/debug 页面。
- Runtime Capability 清楚但不压主体验。
- Debug 完整保留但默认折叠。
- 中文主流程自然。
- 英文主流程不残留中文 UI 文案。
- 移动端主流程不横向溢出。
- `npm run check` 通过。

## 16. 下一阶段建议

下一阶段不应继续泛化美化，而应提升真实 grounding 能力：

1. 强化 DeepSeek Reality Intake 的结构化抽取质量。
2. 增强外部现实来源检索与引用回放。
3. 提升现实节点、现实压力和缺失信息的可解释性。
4. 让路径事件更少模板化、更贴近用户材料。
5. 建立评估集，区分 UI 完整度和真实推演准确度。
6. 继续保持命理为调权层，而不是事实生成层。

最终目标：用户不是相信“命理说了什么”，而是相信 Astraloom 先认真读懂现实，再把几种可能路径以有依据、有不确定性、有观察点的方式展开给他们看。
