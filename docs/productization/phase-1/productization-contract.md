# Astraloom 产品化权威契约

## 1. 目的与裁决顺序

本契约把白皮书 v35 的工程可执行要求固化为后续产品化工作的唯一工作边界，而不复制白皮书。裁决顺序为：

1. 白皮书 v35 对“产品应具备什么”的要求（特别是第 5、8–11、13–18、21–29、31 章）；
2. 已验收 V2 Core 对“现有核心已经如何工作”的可执行事实；
3. 仓库安全与工程约束。

若第 1 与第 2/3 层实质冲突，停止扩大实现，记录在 `decision-register.md`；本契约不以文档文字消除冲突。

## 2. 产品定义与核心价值

Astraloom 是一个以用户提供的现实情境、明确假设和可追溯证据为输入的关系/决策沙盘。它将情境转为可确认的人物、可审阅的只读关系图、可重现的情景轨迹、事件账本与证据支持的报告，使用户比较可行路径和行动干预，而不是获得确定性预言。

核心闭环（白皮书 5、8、13、21、24 章）：

`Seed Context -> Key People 确认 -> Agent Profiles -> Read-only Relation Graph -> Simulation Ticks -> Event Logs -> Claims -> Report -> Feedback Calibration`

## 3. 首版范围

### Track A：首个可用闭环

- 单一明确问题；30 或 90 天窗口；职业选择与工作协作为首个受控领域。
- 用户输入情境，确认/合并/删除/重命名关键人物，查看只读图谱，启动一次异步运行，查看带事件证据的多路径结果与保守策略建议。
- 首个 Alpha 不承诺真实世界概率；展示的频率必须来自真实轨迹样本、固定 seed、样本数、版本和假设说明（白皮书 5.5、13.8、21；V2 方向）。

### Track B：首版受限边界

- 单主题、1/3/5 年的粗粒度“长期气候”视图；不得输出日级预测、确定性命运或脱离图谱/事件的营销文章。
- 不进入 Alpha。只在 Track A 全链路与安全/成本门槛达标后，以单独契约与 Golden Cases 启动。

## 4. 不可破坏原则

- 人物先于推演；每个重要人物均有 Agent Profile，每条重要关系均有 Relation Edge（白皮书 5.1–5.2、8.2、13.5–13.6）。
- 图谱对用户只读；用户可确认、合并、删除、重命名、补充人物，不能编辑边权（白皮书 5.2.3、9.6、17.10、25.7）。
- Event Log 先于 Claim；重要 Claim 必有 `evidence_event_ids`，报告只能消费既有证据（白皮书 5.4、5.7、13.7、21.12–21.15、22.8）。
- 真实世界证据与模拟事件是两套账本；模拟 Event 不是现实发生证明。未知、推断、争议信息必须作为假设显式呈现（V2 核心契约）。
- 高风险输入先走 SafetyVerifier 降级，再决定生成、解锁或人工复核；付费绝不能绕过降级（白皮书 5.3.6、15、23、25.17）。
- 免费预览保持低成本，不能默认进行完整 NPC 深扫；付费只解锁已有证据/策略深度，不能提高置信度、制造 Claim 或改变风险等级（白皮书 5.4.4、5.7.5、6、19）。
- 用户拥有的数据必须有认证、隔离、同意、删除请求、导出和审计边界（白皮书 10.7–10.10、15、20.14、28）。

## 5. 权威数据对象与集成原则

首版权威对象为 `SeedContext`、`KeyPerson`、`AgentProfile`、`RelationEdge`、`SimulationRun`、`SimulationTick`、`EventLog`、`Claim`、`Report`、`FeedbackLog`、`ConsentEvent`、`GenerationJob`、`Entitlement` 与 `SupportTicket`（白皮书 5、10、20、24）。每个生成对象必须携带版本、trace 与来源；服务端写入必须幂等且可审计。

V2 Core 是这些对象的**确定性核心消费者/生产者**，不是产品数据库或 Web 后端的替代品。接入顺序必须是：边界适配与验证 -> 带用户归属的持久化 -> API/异步 job -> 页面消费 -> 端到端和 Golden Case 验收。不得把 `local-*`、`in-memory-*`、`adapter` 或独立测试模块宣传为后端已经完成。

## 6. No-Go

- 通用聊天入口、算命/命理/读心/确定命运、CRM 式编辑关系图、运行中的连续 RPG 选择。
- Alpha 之前的 Track B、免费 NPC 深扫、社交/社区/排行榜、原生客户端、广域人生预测。
- 未经单独授权的真实 LLM 扩展、生产数据库写入、Stripe 写入、解锁、服务角色权限、全量删除或迁移。
- 未通过事件证据、真实证据边界和安全校验的报告文本、付费文案或置信度提升。

## 7. 阶段定义

- **Alpha**：5–10 名内部受邀用户能完成 Track A；认证、用户隔离、异步 job、只读图谱、Event/Claim/Report 证据链、安全降级、失败恢复均可人工验收。
- **完整 MVP**：所有白皮书首版必需闭环、付费/额度、删除/导出/支持、质量/成本观测及发布前安全门槛达到可重复验收。
- **封闭 Beta**：受控招募用户在真实运行环境使用 MVP；质量、成本、安全、退款、支持和反馈指标按第 26–29 章周节奏决策通过/回炉/停止。
- **Launch**：法务交付、生产监控/报警/回滚、值守、支持 SLA、变更控制和 Launch 门槛均已真实演练。

## 8. 契约变更流程

提出者创建一个含“白皮书章节、V2/仓库证据、用户影响、成本/安全影响、替代方案、迁移与回滚”的决策条目。只有会改变产品边界、商业模式、安全、成本或不可逆架构的事项需创始人确认；一般技术实现采用路线图的推荐默认方案。确认后才可修改本契约和对应的产品文档，不能以代码先行反推产品决定。
